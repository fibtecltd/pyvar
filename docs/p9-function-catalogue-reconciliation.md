# Function catalogue reconciliation

Verified 2026-08-02, in response to an independent strategic assessment flagging that
`pyvar_functions.csv` (382 rows) has never been reconciled against the live engine/API.

## The short version

**`pyvar_functions.csv` is a stale, manually-curated snapshot from the P2 implementation
phase, not the current source of truth.** `scripts/generate_function_catalog.py`'s own
module docstring already says so:

> `pyvar_functions.csv` is stale (382 rows vs 385 real routes — market-risk alone grew by
> 3 since it was generated)

The current, authoritative catalogue is **`portal/functions.json`** — generated by that
script directly from the live OpenAPI schema (`main.create_app().openapi()`) and each
route's engine docstring. It is not wired into CI; regenerate and commit it by hand
whenever routes, schemas, or engine docstrings change (`python3
scripts/generate_function_catalog.py`).

## What was actually verified

| Domain | `pyvar_functions.csv` | `portal/functions.json` (live) | Match? |
|---|---:|---:|---|
| Market Risk | 68 | 71 | **No — +3** |
| Derivatives & Pricing | 62 | 62 | Yes |
| Credit Risk | 55 | 55 | Yes |
| Portfolio Analytics | 50 | 50 | Yes |
| Operational Risk | 44 | 44 | Yes |
| Liquidity Risk | 40 | 40 | Yes |
| ALM & Balance Sheet | 33 | 33 | Yes |
| Regulatory & Compliance | 30 | 30 | Yes |
| **Total** | **382** | **385** | |

Seven of eight domains match exactly. Only Market Risk differs, and only in the
direction the generator script already documented.

## Why Market Risk specifically, and a caveat on precision

Comparing `engine/`'s Market-Risk-grouped files directly (`montecarlo.py`,
`expected_shortfall.py`, `stress.py`, `greeks.py`, `pnl_attribution.py`,
`backtesting.py`, `volatility.py`, `var_models.py`, `frtb.py`, `metrics.py`) against
both the CSV and the live JSON shows the gap is not simply "3 uncatalogued
capabilities." At least part of it is legacy route duplication: `engine/metrics.py`
contains four older, lower-level functions (`compute_cvar`, `compute_rolling_var`,
`compute_loss_percentiles`, `compute_breaches`) that overlap conceptually with
newer, already-catalogued entries (`conditional_var_es`, `rolling_var_backtest`,
`var_fan_chart`) but are wired as **separate live API routes**
(`api/routes/market_risk.py` imports all four under `_e_compute_*` aliases) and
therefore appear as four additional entries in `portal/functions.json`, which counts
live routes, not deduplicated capabilities.

**This means the 382 → 385 gap is a mix of genuine route growth and route-level
duplication that the original hand-curated CSV deliberately (or incidentally)
collapsed.** Identifying the exact 3 net-new Market Risk entries with full confidence
would require a careful name-by-name pass beyond what automated matching can do
reliably (display-name formatting differs enough between the two sources — "P&L" vs
"Pnl", parenthetical suffixes, word order — that naive string matching produces both
false positives and false negatives). That precise mapping is not done here and is
flagged as a known gap rather than guessed at.

## What this means going forward

- **Do not quote "382 functions" as a current fact.** Historical planning documents
  (`docs/pyvar_release_plan.md`, `docs/pyvar_notes.md`) correctly used 382 as the P2
  implementation target at the time and are left as historical record, not live claims.
- **Treat `portal/functions.json` as canonical** for "what pyvar currently exposes."
  It is generated from the live OpenAPI schema — it cannot drift from what the API
  actually does, only from when it was last regenerated (last run: 2026-08-02, this
  session).
- **`pyvar_functions.csv`'s ongoing purpose, if any, needs an explicit decision.** As a
  deduplicated, human-curated capability list it may still be useful for documentation
  or planning purposes — but it should carry a visible note that it is not
  auto-synced and may undercount live routes, rather than being read as a precise,
  current inventory.
