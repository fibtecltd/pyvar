# Portal assistant eval (Phase 0)

The kernel this harness measures (prompts, graders, cost, schema checker, record trimmer, scrub) lives in `assistant/`; the modules of the same names here are shims that resolve to the same module objects.

Measures whether Claude Haiku 5.5 can power the menu-driven help panel described in
`docs/plan-portal-ai-assistant.md`: a visitor picks a function and an action from fixed menus and types
nothing. Four actions are generated by the model; everything else in the menus is static text.

| Action | What the model writes | How it is checked |
|---|---|---|
| `explain` | what the function does, 3 to 5 sentences | graders: names, numbers, scope, wording, length |
| `when` | when to use it and when a sibling fits better | the same, with the sibling list |
| `example:typical` / `example:stress` | one JSON request body | the real request schema (shape and types), up to 3 tries |
| `compare` | how it differs from a sibling | the same as `explain`, both names must appear |

A pass from the graders is necessary, not sufficient. `judge.py` asks a stronger model four yes/no questions
about a sample (faithful, useful, plausible values), and a human should read a handful of answers.

## Run it

```bash
# 1. The case set (needs the project environment: it imports the app for the OpenAPI schema, so first
#    pip install -r requirements.txt -r requirements-ci.txt, which brings numpy, scipy and numba)
APP_ENV=test python scripts/assistant_eval/cases.py --out $WORK/cases.jsonl          # a sample
APP_ENV=test python scripts/assistant_eval/cases.py --all --out $WORK/cases_all.jsonl # every function

# 2. Prove the harness first, no API and no cost: the oracle must pass all, the null must pass none
python scripts/assistant_eval/run_eval.py --cases $WORK/cases.jsonl --out $WORK/oracle --oracle
python scripts/assistant_eval/run_eval.py --cases $WORK/cases.jsonl --out $WORK/null --null

# 3. The paid run (pip install -r scripts/assistant_eval/requirements.txt; needs an Anthropic key)
python scripts/assistant_eval/run_eval.py --cases $WORK/cases.jsonl --out $WORK/haiku \
    --model claude-haiku-5-5 --max-usd 3
python scripts/assistant_eval/judge.py --cases $WORK/cases.jsonl --run $WORK/haiku --per-intent 12 --max-usd 3

# 4. Optional: only some actions (explain, when, compare, example:typical, example:stress), for both tools
python scripts/assistant_eval/run_eval.py --cases $WORK/cases.jsonl --out $WORK/v2 --only explain,when,compare
python scripts/assistant_eval/judge.py --cases $WORK/cases.jsonl --run $WORK/v2 --only explain,when,compare \
    --per-intent 80 --max-usd 2

# 5. After a grader change: grade a finished run's saved answers again, no API and no cost
python scripts/assistant_eval/regrade.py --cases $WORK/cases.jsonl --run $WORK/haiku

# 6. Phase 0b (docs/assistant-phase0-results.md section 9): does the model beat static text?
python scripts/assistant_eval/side_by_side.py pick --cases $WORK/cases.jsonl                 # 12 case ids
python scripts/assistant_eval/side_by_side.py export --run $WORK/haiku_v2 --ids ID ... > answers.json
python scripts/assistant_eval/side_by_side.py build --cases $WORK/cases.jsonl --answers answers.json \
    --out blind.html --key key.json            # the page for the reader; keep key.json away from them
#    and a cheaper judge against the Opus verdicts already there (--tag keeps the Opus files):
python scripts/assistant_eval/judge.py --cases $WORK/cases.jsonl --run $WORK/haiku_v2 \
    --only explain,when,compare --per-intent 80 --judge-model claude-haiku-5-5 --tag haiku
python scripts/assistant_eval/compare_judges.py --actions explain,when,compare \
    --pair $WORK/haiku_v2/judgments.jsonl $WORK/haiku_v2/judgments_haiku.jsonl

# 7. Opus's recall (docs/assistant-phase0-results.md 9.11): a person reads answers Opus passed
python scripts/assistant_eval/recall_check.py pick   --cases $WORK/cases.jsonl --run $WORK/haiku_v4   # the draw
python scripts/assistant_eval/recall_check.py export --cases $WORK/cases.jsonl --run $WORK/haiku_v4 > stage1.json
python scripts/assistant_eval/recall_check.py build  --cases $WORK/cases.jsonl --answers stage1.json \
    --out check.html --key key.json            # --stage 2 on export for the second batch; keep key.json from the reader

# 8. Tier measurement (docs/assistant-plan-tier-measurement.md): bigger writers, repeated draws
python scripts/assistant_eval/run_eval.py --cases $WORK/cases.jsonl --out $WORK/opus_d1 \
    --model claude-opus-5-5 --effort low --only explain,when,compare --max-usd 4.1
python scripts/assistant_eval/run_eval.py --cases $WORK/cases.jsonl --out $WORK/sonnet_r3 \
    --model claude-sonnet-5-5 --only-ids ID1,ID2 --reps 8 --max-usd 0.6    # the 8 persistent cases, 8 draws
python scripts/assistant_eval/judge.py --cases $WORK/cases.jsonl --run $WORK/sonnet_r3 \
    --all-reps --per-intent 1000 --max-usd 1.8                             # every draw, not only draw 0
python scripts/assistant_eval/detectors.py --cases $WORK/cases.jsonl --run $WORK/sonnet_r3   # no model

# 9. Typed questions (plan 1, sections 3 and 5): a model with three read-only tools answers typed text
python scripts/assistant_eval/typed_cases.py --out $WORK/typed_cases.jsonl     # 260 cases, no app, no API
python scripts/assistant_eval/run_typed.py --cases $WORK/typed_cases.jsonl --out $WORK/typed_oracle --oracle
python scripts/assistant_eval/run_typed.py --cases $WORK/typed_cases.jsonl --out $WORK/typed_null --null
python scripts/assistant_eval/run_typed.py --cases $WORK/typed_cases.jsonl --out $WORK/typed_haiku \
    --model claude-haiku-5-5 --max-usd 0.3                                       # paid; --categories, --only-ids, --reps
python scripts/assistant_eval/judge.py --kind typed --cases $WORK/typed_cases.jsonl --run $WORK/typed_haiku \
    --in-scope-only --max-usd 3
```

`--effort` (low, medium, high, xhigh, max; default low, the level of every Phase 0 run) is sent as
`output_config.effort`. `summary.json` of every run records the writer model id, the model ids the API reported
serving, the effort, `prompt_version`, and under `code` the git commit that last touched `prompts.py` and
`graders.py`, whether they have uncommitted edits (`dirty`) and their sha256, so a run says which text produced it.
`--tries N` gives every action up to N writer calls: after a grader failure the flags go back to the writer (what the bank pipeline would do), `model_tries` counts the calls, `static_fallback` marks an answer that still fails, and `summary.json` reports first-try and final passes and the histogram of calls (unset: example values get 3 calls, text actions 1). `--only-ids` runs the named cases only (an id not in `--cases` is an error); `--reps N` repeats each case N times
(draw numbers 0 to N-1). The judge samples draw 0 unless `--all-reps` is given.

**Typed questions.** The set is `typed_cases.py` (templates over `portal/functions.json`: A how-to 50, B which
function 35, C example values 30, D not in the record 30, I multi-function, long or non-English 11) plus
`typed_adversarial.jsonl` (70 cases written by hand: E advice 15, F off-topic 14, G injection 14, H pasted keys 8,
I ambiguous or non-English 19) and the generated rest of E to H (E 10, F 6, G 11, H 7): 260 in all, 175 in scope for
the flag-rate rule (A to D, I). Every case has machine-checkable `expect` fields; nobody labels answers. The file
is deterministic and its sha256 is pinned in `tests/test_assistant_typed.py` (a catalogue change fails that test
on purpose: re-pin it with the reason). Tools run in-process (`typed_tools.py`, no network): `search_functions`,
`get_function` (returns `cases.trim_record`), `propose_parameters` (validates type and required flags against
the catalogue's parameter list, and its numeric bounds, which the catalogue does not state today). At most 4
tool turns, then a last call with `tool_choice` none. The question is scrubbed (`scrub.py`: `pyvar_` keys, JWTs,
`sk-ant-` keys, long hex) before any model call, and a question that still looks like a key is never sent.
`graders.grade_typed` checks the final answer against the union of what the tools returned; `typed_oracle.py`
and `--oracle`/`--null` prove it with no API (oracle 260 of 260, null 0 of 260).

`detectors.py` holds one deterministic known-error detector for each of the 8 cases Opus flagged on two or more
of four draws. Six rest on claims the results document describes; `conduct_risk_metric:compare:model_risk_assessment`
and `esg_score_integration:when` are marked `hypothesis`, because the flags CSVs hold only F/P and the grader
failure, not Opus's issue text. A clean detector result does not prove an answer correct: it only shows the
known claim is absent.

`--max-usd` is a hard cap: when reached, new cases are skipped (and counted as skipped, not failed). A run
resumes where it stopped. Output per run: `results.jsonl`, `errors.jsonl`, `traces/`, `summary.json`, which
names the `prompt_version` that produced it (`prompts.PROMPT_VERSION`; v1 was the first paid run, v2 states a
character budget and three rules in each text task, v3 stops the guide using its own words, "the record" and
"sibling", which a visitor cannot interpret, and a grader checks it, v4 withdraws the claim that the
documentation lacks something, which Opus found false in 6 of 22 flagged answers, and a grader checks that too, v5 stops it crediting any statement to "pyvar's documentation" (7 of 21 flags over two v4 draws), and a grader checks that too). `prompts.py` carries v4 (`v4-2026-11-09`), the candidate: v5 was measured and not adopted (docs/assistant-phase0-results.md 9.14), though the `no_source_claims` grader it added stays. The judge's sample inside an action is in a fixed hash
order, so `--per-intent 80` starts with the answers `--per-intent 40` judged: runs can be compared case by
case. The judge overwrites `judgments.jsonl` in the run directory; copy it first if you want the old one.

## How to read the output

- Scored rows have `status: ok`. `truncated` (hit `max_tokens`) and `refusal` are counted and shown, never
  averaged in as wrong. Attempts that produced no answer (API error after retries, timeout, wrong served
  model) are in `errors.jsonl`.
- Cost and tokens come from the API's `usage` at the rate of the model that served the call
  (`cost.py`, from the Claude API reference cached 2026-10-06: verify against live pricing).
- Pass rates carry a 95% Wilson interval. With 134 cases per action the interval is about +/- 8 points at
  90%, so a gap smaller than that is noise.

## What it cannot tell you

- Whether prose is true beyond the record. The catalogue has a one-line summary, a formula and symbol map, and
  often a short description. Each parameter carries the `Args:` text of its engine docstring (added to the
  API models in the same PR; before it, none of the 1,577 had one), and the record shows that text to the
  model. The descriptions are unreviewed beyond spot checks, so a wrong or thin one is a source of wrong
  answers that the mechanical graders cannot see, because they only check against the record.
- Whether example values are plausible or whether the API accepts them: the schemas carry no numeric bounds
  (the descriptions sometimes state a range in words), and arrays are kept to 10 items, which a function
  that needs a longer series may reject.
- How a real visitor behaves. There is no visitor text in this design; the cases come from the catalogue.
